Campaign Mode Map

An autonomous MD benchmarking run: the model designs the plan and proposes knob values, but every irreversible decision — what the script says, when to stop, what counts as best — is made by deterministic Python. Two human gates sit between them.

01Three turns, two gates

A campaign is not one long autonomous run. It is three chat turns separated by two points where the run stops dead until a human acts, plus an optional fourth turn for visual analysis. The loop only becomes autonomous after the template is approved.

02The script is generated once — then never again

This is the design decision the whole mode is built around. If each iteration asked the model for a fresh LAMMPS script, trials would differ in ways nobody tracked, and comparing a metric across them would be meaningless. So generation happens exactly once, behind gate 2, and every iteration afterwards is a plain string substitution into the approved bytes.

03One iteration, six tool calls

After approval the orchestrator runs the whole campaign inside a single ReAct trace — which is why the recursion limit is raised to 200 (roughly 20 iterations × 6 tools plus wrapping). The order is fixed, and the model steers only at step 2.

04Who decides to stop

Not the model. campaign_check_stop() reads plan.json, control.json and trials.jsonl from disk and evaluates guards in a fixed order — first match wins. Two of the seven written guards are currently commented out in the source.

  1. 1user_cancelledcontrol.json says cancelled — exits, and the report is still generated
  2. 2user_pausedcontrol.json says paused — exits with no report, resumable later
  3. 3max_iterationstrial count has reached plan.max_iterations
  4. 4target_hitan explicit objective.target is set and the best value meets it, direction-aware
  5. 5consecutive_failuresthree trials in a row failed — aborts cleanly and reports what completed
  6. 6no_improvementdisabled: the metric can pin at 0.0, so patience fired on an artifact rather than real convergence
  7. 7convergencedisabled for the same reason — campaigns now run to max_iterations unless a human or a failure stops them
Both disabled guards are commented out in place rather than deleted, with the reason written next to them: metric saturation made plateau-detection cut campaigns short. They come back when the crack metric is trustworthy.

05How a human interrupts a running loop

The loop is inside a single blocking trace, so control does not go through the chat — it goes through a file. Three HTTP endpoints flip control.json, and the loop notices at its next check_stop(). Resume needs a second action, because flipping the flag back does not restart a trace that has already ended.

06Everything durable is a file

The model is told never to remember trial history. It calls campaign_get_state() at the top of every iteration instead, so a restarted server, a reloaded page or a resumed session all read the same truth.

Duplicate protection lives in the reader, not the writer: _read_trials drops a row whose (iteration, run_folder) pair it has already seen, so an interrupted turn that records the same finished run twice cannot inflate the trial count and end the campaign early. Rows with no run_folder are never collapsed — two distinct failures look alike but are both real.

07What the browser sees

Tools push SSE events onto the session queue as they run, so the banner, the progress table and the live trajectory viewer stay in step with a loop that never returns to the chat until it is finished.
